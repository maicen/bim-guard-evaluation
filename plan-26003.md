# Evaluation Strategy: bim-guard-evaluation → bim-guard

## Context

`bim-guard-evaluation` is the dedicated accuracy-benchmarking and research companion to `bim-guard`, a BIM compliance-checking platform. The eval repo already contains 9 evaluation scripts, an NLP annotation module, gold-standard datasets, and research artifacts — but they run in isolation with no unified orchestration, no regression tracking, no CI/CD, and no black-box API testing. This plan connects the dots and fills the highest-value gaps.

## 3. Unified Orchestration

### 3.1 Create `eval/eval_config.py` — shared foundation

Deduplicate the `BIMGUARD_PATH` / `sys.path` boilerplate repeated in all 9 scripts into one import. Also provides:

- Result storage directory (`eval/results/`)
- Standard JSON result schema: `{eval_id, tier, status, passed, failed, total, score, duration_s, bimguard_commit, eval_commit, details}`
- Baseline loading/comparison helpers
- Run-ID generation (ISO timestamp)

### 3.2 Create `eval/run_all.py` — orchestrator

Single entry point that runs evaluations in tier order:

- `--tier N` — run up to tier N only (default: 2)
- `--smoke` — fast subsets per script
- `--compare-baseline` — compare to stored baselines, exit 1 on regression
- `--update-baseline` — promote current results
- `--json` — aggregate manifest output

Each script runs as a subprocess to avoid module-level singleton pollution (consistent with bim-guard's own test pattern).

### 3.3 Add `--json` to each eval script

Each script gains a `--json` flag that writes structured results to `eval/results/<script_name>_<timestamp>.json` alongside existing print output. Non-breaking, additive change.

**Implementation order:**

1. `eval/eval_config.py` (shared module)
2. `--json` on `score_nlp_annotation.py` (simplest, proves pattern)
3. Propagate `--json` to remaining scripts
4. `eval/run_all.py` orchestrator
5. `eval/baselines/` directory with initial captures

## 4. New Evaluations (Prioritized)

### Priority 1: Mode A — Black-Box API Evaluation

**File:** `eval/test_api_endpoints.py`

The documented Web API evaluation mode doesn't exist yet. Two approaches, used together:

**In-process TestClient** (fast, default):

```python
from starlette.testclient import TestClient
from app.main import app
client = TestClient(app)
```

**Live HTTP** (true black-box, via `--live` flag + `BIMGUARD_URL` env var):
Uses `httpx` against a running server for real network/CORS/middleware behavior.

**Scope:** ~40 tests across router groups — rules CRUD, analyze, BCF v2.1, projects, documents, dashboard, digital inspector, bsDD, CDE, naming config, settings, events.

### Priority 2: End-to-End API Roundtrip

**File:** `eval/test_e2e_roundtrip.py`

The single most valuable integration test — exercises the complete user workflow:

1. POST PDF → `/api/rules/extract` → verify extracted rules
2. POST IFC → `/api/analyze/upload` → trigger analysis run
3. Poll `/api/events/{project_id}` for completion
4. GET BCF export → validate ZIP structure and topic count
5. Compare rule count and issue count to expected baselines

### Priority 3: Regression Baseline System

**Directory:** `eval/baselines/` — one `.baseline.json` per eval script

Each baseline stores: creation timestamp, both repos' commit hashes, aggregate scores, per-category metrics.

**Comparison logic** (`eval/compare_baselines.py`):

- Score delta (current vs baseline)
- Individual test regressions/improvements
- Numeric metric drift (fail on >5% drop in recall/precision)
- Performance: 1.5x tolerance for hardware variance

Baselines update only via explicit `--update-baseline`, never automatically.

### Priority 4: Contract Stability Tests

**File:** `eval/test_contracts.py`

Guard against silent breakage when bim-guard renames modules or changes signatures:

- Verify every `app.*` import path resolves
- Key function signatures match expected parameters
- `CODE_TO_IFC_MAP` size, `_PROPERTY_ALIASES` keys, `ClearanceConfig` loading

### Priority 5: Expanded Gold Standards

Add gold-standard answer keys for additional building code sections beyond stairs (CODE 9.8):

- Fire separation (CODE 9.10)
- Plumbing (CODE 7)

Uses the existing `score_rule_extraction.py` harness with no new infrastructure — just new `eval_gold_code_*.py` data files.

### Priority 6: Mode Parity Verification

**File:** `eval/test_mode_parity.py`

Verify that Mode A (API) and Mode B (import) produce identical results for the same inputs — rule extraction, analysis results, BCF export structure.

## 5. When to Use Mode A vs Mode B

| Use Case | Mode | Why |
| ---------- | ------ | ----- |
| Algorithm accuracy / confusion matrices | **B (Import)** | Direct access to internals, no serialization overhead |
| Performance profiling (CPU/memory) | **B (Import)** | Can instrument individual functions |
| Thesis figure generation | **B (Import)** | Needs raw data structures |
| API contract compliance | **A (API)** | Tests the real HTTP surface |
| Error handling (400/404/500) | **A (API)** | Tests middleware + validation |
| End-to-end user workflow | **A (API)** | Tests the path users actually take |
| Serialization correctness | **A (API)** | Tests Pydantic → JSON → client path |
| Verifying both paths agree | **Both** | Mode parity tests |

## 6. CI/CD Integration

### GitHub Actions: `bim-guard-evaluation/.github/workflows/eval.yml`

| Job | Trigger | Tiers | Duration |
| ----- | --------- | ------- | ---------- |
| `tier-0-unit` | Every PR | 0 | ~5s |
| `tier-1-component` | Every PR | 0+1 | ~30s (checks out bim-guard adjacent) |
| `tier-2-integration` | Push to main | 0+1+2 | ~5min |
| `tier-3-system` | Weekly schedule | 0+1+2+3 | ~45min |
| `compare-baselines` | After tiers complete | — | ~10s, fails on regression |

### Cross-repo trigger: `bim-guard/.github/workflows/trigger-eval.yml`

When bim-guard pushes changes to `app/modules/**`, `app/services/**`, `app/engines/**`, or `app/api/**`, dispatch `repository_dispatch` to the eval repo to run tiers 0+1+2. Catches upstream regressions before they propagate.
